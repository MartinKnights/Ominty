# Niri + DMS Aesthetics — Design

**Date:** 2026-10-14
**Status:** Approved (Approach B — custom shaders + matugen theming)
**Scope:** niri compositor animations/glow + DankMaterialShell theming + TTS/STT popups

> **Correction (2026-10-14, after implementation research):** niri 26.04's `custom-shader`
> takes an **inline GLSL string**, not a file path — `src/niri.rs:1568-1573` passes the
> config string straight to the shader compiler. The shader is therefore embedded in a
> matugen-generated KDL file rather than a separate `.frag`. The popups read a
> matugen-generated palette file (`~/.config/ominty/theme/palette.json`) rather than
> `dms-colors.json`. See `2026-10-14-niri-dms-aesthetics.md` for the authoritative
> implementation detail; §3.2 / §3.3 / §8 below are superseded where they differ.

## 1. Goal

Four enhancements to the niri + DankMaterialShell (DMS) desktop:

1. **Open animation** — a dot at the window centre grows, expands horizontally into a
   line, then grows vertically into the full window rectangle, drawn in the current
   themed border colour with an inner + outer glow; the window content fades in as the
   shape completes.
2. **Close animation** — the window iris-converges from its four corners to a centre dot
   and fades to nothing; the glow is cut instantly; total ≤ 1 s.
3. **Persistent glow** — every window carries a themed glow, stronger outside than inside.
4. **TTS/STT theming** — the `ominty-voice` and `ominty-tts` Quickshell popups
   automatically follow the DMS theme.

## 2. Environment & constraints

| Item | Value |
|---|---|
| Compositor | niri **26.04** |
| Shell | DankMaterialShell **v1.7-beta** |
| Theming | matugen (driven by DMS) |
| Agent privileges | **no sudo** — user-space config only |
| Shader API | unstable; niri gives no backwards-compat guarantee |

### 2.1 Verified niri 26.04 facts

- `custom-shader` takes an **inline GLSL string** (`custom-shader r"…"`); niri passes the
  string **directly** as shader source (`src/niri.rs:1568-1573`). The `path="…"` property
  form exists only on newer `main`, not in 26.04.
- `cubic-bezier` curve is supported.
- `animations { on }` resets the `off` flag (`if part.on { self.off = false }`) — the
  existing `animations { off }` line need **not** be removed.
- A later `window-open` / `window-close` block **replaces** the earlier one.
- `border { on }` resets `off`; `shadow { on }` enables the shadow (same on/off merge
  pattern as animations).
- With a custom shader, niri bakes **border + focus-ring + shadow** into `niri_tex` and
  the shader draws over an area **larger** than the window.
- The generated KDL file is added to niri's `Includes` → niri **watches and hot-reloads** it.

### 2.2 Verified DMS facts

- `runUserMatugenTemplates` defaults to **true** (`Common/settings/SettingsSpec.js:37`).
- User matugen config = `~/.config/matugen/config.toml` (**does not exist yet**).
- DMS's niri template uses `{{colors.primary.default.hex}}` for the border/focus-ring
  active colour.
- The full palette is written to `~/.local/state/DankMaterialShell/dms-colors.json` on
  every theme change.

## 3. Architecture

### 3.1 Theming pipeline

```
wallpaper / seed colour
        │
        ▼
  dms matugen generate
        ├── DMS templates  ──► ~/.config/niri/dms/colors.kdl   (existing, untouched)
        └── user templates ──► ~/.config/niri/dms/ominty-theme.kdl  (new)
                           ──► ~/.config/ominty/theme/palette.json   (new)
```

- `~/.config/matugen/config.toml` (new) declares three `[templates.*]` entries.
- All three use `{{colors.primary.default.hex}}` — the same variable DMS's niri template
  uses — so the shader/glow colour is guaranteed to match the border colour.
- Because the shader files live in niri's `Includes`, niri hot-reloads them when matugen
  rewrites them.

### 3.2 niri config wiring

`config.kdl` keeps `animations { off }` (line 158) untouched. Two new includes are
appended **after** `dms/windowrules.kdl` (line 349), because the last matching rule wins:

```kdl
include "dms/animations.kdl"
include "dms/glow.kdl"
```

**`~/.config/niri/dms/ominty-theme.kdl`** (generated by matugen; the `animations` block
carries the shaders **inline**, with the accent colour baked in):

```kdl
animations {
    on
    window-open {
        duration-ms 350
        curve "cubic-bezier" 0.2 0.8 0.2 1
        custom-shader r"
            const vec3 OMINTY_ACCENT = vec3({{colors.primary.default.red}}/255.0, …);
            vec4 open_color(vec3 coords_geo, vec3 size_geo) { … }
        "
    }
    window-close {
        duration-ms 300
        curve "cubic-bezier" 0.4 0 0.2 1
        custom-shader r"
            vec4 close_color(vec3 coords_geo, vec3 size_geo) { … }
        "
    }
}
```

Full shader source: see `2026-10-14-niri-dms-aesthetics.md` §4 Tasks 5-6.

**`~/.config/niri/dms/glow.kdl`** (generated by matugen; shown post-substitution):

```kdl
layout {
    border {
        on
        width 2
        active-color   "<primary>"
        inactive-color "<outline>"
    }
    shadow {
        on
        softness 40
        spread 8
        offset x=0 y=0
        color "<primary>40"
    }
}
```

### 3.3 Shader design

Both shaders implement `vec4 open_color(vec3 coords_geo, vec3 size_geo)` /
`vec4 close_color(...)` and return **premultiplied** colour. `coords_geo.xy ∈ [0,1]` over
the window geometry (may be <0 / >1 outside); `size_geo.xy` is the window size in logical
px; `niri_progress ∈ [0,1]` is the eased progress; `niri_tex` is the baked window texture.

**`open.frag`** — a signed-distance-field (SDF) rounded rectangle whose half-extents
animate:

| progress | shape |
|---|---|
| 0.00 – 0.30 | dot grows from 0 to a small radius |
| 0.30 – 0.60 | dot expands horizontally into a line |
| 0.60 – 0.90 | line expands vertically into the window rectangle |
| 0.90 – 1.00 | content cross-fades in; synthetic frame fades out |

- `mask = smoothstep(edge, edge+aa, -sd)` reveals the window texture inside the shape.
- `frame = exp(-abs(sd)/glow_width)` draws the glow around the shape edge (both sides →
  inner + outer glow).
- Final = `texture(niri_tex, …) * mask * content_alpha + border_color * frame * intensity`.
- At `progress ≥ 0.95` the result cross-fades to the **full** texture so the real
  border/shadow (which lie outside the geometry) are shown exactly.

**`close.frag`** — the reverse SDF animation (rect → line → dot → fade). No synthetic
glow; the shadow (outside the geometry) is masked out from the first frame, so the glow
is cut instantly.

### 3.4 TTS/STT theming

The popups are separate Quickshell instances (`quickshell -c ominty-voice`, `-c ominty-tts`)
and cannot import DMS's `Appearance` singleton. Instead each popup reads
`~/.local/state/DankMaterialShell/dms-colors.json` via `FileView { watchChanges: true }`
and maps:

| popup role | palette key |
|---|---|
| panel background | `colors.<mode>.surface_container` |
| primary text | `colors.<mode>.on_surface` |
| accent | `colors.<mode>.primary` |
| error | `colors.<mode>.error` |
| border | `colors.<mode>.outline_variant` |

The popup sources are symlinks into the ominty-core repo, so edits are made in the repo.

## 4. Data flow

1. User changes wallpaper/theme in DMS.
2. DMS runs `dms matugen generate` → matugen renders DMS templates **and** user templates.
3. `open.frag`, `close.frag`, `glow.kdl` are rewritten with the new palette.
4. niri detects the changed include files → reloads config → new shaders/glow take effect
   immediately.
5. DMS writes `dms-colors.json` → the popups' `FileView` fires → popups re-theme.

## 5. Error handling

- **matugen user templates fail** → DMS logs the error; the shader files keep their
  previous contents (niri keeps working). Fallback: a systemd `path` unit watching
  `dms-colors.json` that regenerates the shaders with a small script.
- **Shader compile error** → niri logs it and falls back to the default animation for that
  window. Mitigation: validate with `niri validate` and test in a scratch config first.
- **`dms-colors.json` missing/malformed** → popups fall back to their current hardcoded
  colours.
- **niri update breaks the shader API** → documented; shaders are isolated in `dms/*.frag`
  and can be disabled by removing the two includes.

## 6. Testing

- `niri validate -c ~/.config/niri/config.kdl` after every config edit.
- Open/close a window and observe the animation; verify the colour matches the border.
- Change the DMS theme and confirm the shader colour + glow + popups all update.
- Verify the popups re-theme live (no restart).
- Confirm `animations { off }` in `config.kdl` is overridden by `animations { on }`.

## 7. Risks & limitations

- **Inner glow** — niri has no native inner glow; the border is a linear bbox gradient,
  not a clean ring falloff. Approximated with a bright border + soft shadow. A true inner
  glow would need a Quickshell overlay (out of scope).
- **Open animation cannot wait for app readiness** — inherent to niri; the shader draws
  the frame then fades the texture in.
- **Shader API instability** — a future niri update could break the shaders.
- **Close glow pop** — masking the shadow from the first close frame causes a small pop;
  tunable.
